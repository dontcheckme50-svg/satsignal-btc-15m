# SATSIGNAL PostgreSQL Storage Design (Draft)

## Scope and safety boundary

This design is for the isolated `supabase-connectivity-probe-v1` branch only.
It does not change application startup, the live Hostless deployment, the
existing SQLite database, GitHub secrets, or Supabase schema. The current
SQLite database remains the source of truth until a separately reviewed
migration is implemented and verified.

## Current storage contract

The current application creates one `PredictionLedger` from
`settings.db_path` during application startup. The ledger is SQLite-specific
and currently owns four tables:

- `predictions`: official prediction locks, probability fields, settlement
  outcomes, BRTI/spot-at-lock metadata, and scoring fields.
- `prediction_observations`: timestamped JSON evidence snapshots.
- `trades`: paper-trade entries, status, fees, P&L, and settlement timestamp.
- `multi_exchange_reference`: independent multi-venue reference snapshots,
  including venue JSON and BRTI/spot/strike comparisons.

The ledger also relies on indexes for contract lookup, settlement status,
observation time ordering, trade contract lookup, and reference history.

## SQLite-specific behavior that must not leak into PostgreSQL

1. Connection setup uses `sqlite3`, `sqlite3.Row`, PRAGMAs, and WAL checks.
2. Schema setup uses `executescript`, `PRAGMA table_info`, and
   `INTEGER PRIMARY KEY AUTOINCREMENT`.
3. Query parameters use SQLite `?` placeholders.
4. Prediction idempotency uses `INSERT OR IGNORE` plus `lastrowid`.
5. Settlement serialization uses `BEGIN IMMEDIATE`.
6. Unsettled-contract discovery uses SQLite `strftime` and `substr`.
7. Storage health uses SQLite `PRAGMA journal_mode` and `quick_check`.

A PostgreSQL implementation must replace these deliberately rather than apply
blind string substitutions.

## PostgreSQL mapping

- Use psycopg 3 with explicit TLS required for Supabase connections.
- Use `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` for record IDs.
- Use `DOUBLE PRECISION` for existing numeric measurement fields.
- Use `BOOLEAN` for logical settled/lock/win fields where the application
  contract is boolean; preserve nullable win fields for unscored records.
- Use `TEXT` for existing ISO timestamps and JSON text initially, minimizing
  conversion risk. JSONB can be considered later as a separately tested change.
- Preserve the partial unique index enforcing one official lock per contract:
  `UNIQUE (contract_ticker) WHERE is_official_lock = TRUE`.
- Use `INSERT ... ON CONFLICT DO NOTHING RETURNING id` for idempotent locks.
- Use row-level locking (`SELECT ... FOR UPDATE`) inside one transaction for
  settlement reconciliation. Do not emulate SQLite's `BEGIN IMMEDIATE`.
- Replace SQLite time-string parsing with explicit application-side UTC
  boundary values or PostgreSQL-native timestamp logic after compatibility
  tests establish the exact legacy timestamp formats.

## Transaction and behavior invariants

1. Each ledger operation owns a bounded connection/transaction scope.
2. Settlement reads and updates for a contract are atomic; two reconcilers
   must not grade the same prediction or trade twice.
3. An official prediction lock remains idempotent per contract.
4. The partial unique constraint remains the final database-level guard
   against duplicate official locks.
5. A failed write rolls back all changes in that operation.
6. Read paths preserve ordering, limits, null handling, and return shapes.
7. Dashboard, forecast, radar, feeds, checkpoint logic, and contract rollover
   must not depend on which backend is selected.

## Implementation sequence

1. Add a PostgreSQL schema module and schema-contract tests on this branch only.
2. Add a separate PostgreSQL ledger implementation; leave
   `PredictionLedger` (SQLite) unchanged.
3. Add backend parity tests for every public ledger method, including
   idempotent locking, observation history, trades, settlement, scoreboard,
   and multi-exchange history.
4. Add a non-destructive SQLite export/validation tool that reads a consistent
   source snapshot and writes only to a separately configured destination.
5. Test migration against a disposable copy and compare table counts,
   primary-key ranges, null counts, unique official-lock counts, and
   deterministic row checksums.
6. Run full regression tests and an isolated Hostless development connection
   test before any production rollout proposal.

## Migration gate

Migration is not approved until all of the following are true:

- Original SQLite file and WAL/SHM state are backed up consistently.
- Source database remains unchanged and readable.
- Destination schema is created only in the dedicated development Supabase
  project.
- Every source table has matching destination row counts.
- Critical invariants and sampled/full-row checksums match.
- Application-level parity tests pass against PostgreSQL.
- Rollback procedure is documented and tested.
- User explicitly approves any production configuration change.
